# 2.8 Summary (Chapter 2 Wrap-Up)

This section serves as a quick recap of the essential CUDA C extensions we've covered in Chapter 2. CUDA C is essentially just standard C, but with a few targeted additions (keywords, syntax, and API functions) that allow us to control the GPU.

Here is the master cheat sheet of everything we've learned, linking back to our deep-dives for each topic:

---

## 2.8.1 Function Declarations

To tell the compiler (`nvcc`) exactly *where* a function should run and *who* can call it, CUDA introduces three execution space specifiers.

> **Deep Dive:** [2.5 Kernel Functions and Threading](./2.5_Kernel_Functions_and_threading.md) & [2.7 Compilation](./2.7_Compilation.md)

| Keyword | Executed On | Callable From | Notes |
| :--- | :--- | :--- | :--- |
| `__global__` | **Device** (GPU) | **Host** (CPU) | This defines a **kernel function** (entry point to the GPU). Must return `void`. |
| `__device__` | **Device** (GPU) | **Device** (GPU) | A helper function that runs on the GPU and can only be called by other GPU functions. |
| `__host__` | **Host** (CPU) | **Host** (CPU) | Standard C/C++ function. If you omit any keyword, it defaults to `__host__`. |

 **Pro Tip:** You can use *both* `__host__ __device__` on a single function! This tells the compiler to generate **two** versions of the compiled code: one for the CPU (SASS/PTX) and one for the GPU. This is incredibly useful for utility functions (like math operations) that both the CPU and GPU need to use.

---

## 2.8.2 Kernel Call and Grid Launch

CUDA extends the standard C function call syntax by adding the "chevron" syntax (`<<< ... >>>`) to configure how many threads the GPU should spawn.

> **Deep Dive:** [2.6 Calling Kernel Functions](./2.6_Calling_kernel_functions.md)

**Syntax:** `kernelName<<< gridDim, blockDim >>>(args...);`

- **`gridDim`**: The number of blocks to launch.
- **`blockDim`**: The number of threads inside each block.
- **Together**: They define the total execution grid (e.g., `ceil(N / 256.0)` blocks of `256` threads each).

These parameters are *only* used when launching a `__global__` kernel. They don't apply to standard C functions.

---

## 2.8.3 Built-in (Predefined) Variables

When a kernel launches, thousands of threads execute the exact same code. To prevent them from working on the exact same piece of data, CUDA provides read-only hardware registers that tell each thread *who they are* and *where they live*.

> **Deep Dive:** [2.5 Kernel Functions and Threading (The Telephone Analogy)](./2.5_Kernel_Functions_and_threading.md)

- **`threadIdx`**: The thread's local ID within its block (e.g., Thread 0 to 255).
- **`blockIdx`**: The ID of the block this thread belongs to.
- **`blockDim`**: The size/dimensions of the block (how many threads are in it).

By combining these, a thread calculates its **global index**:
`int i = blockIdx.x * blockDim.x + threadIdx.x;`

*(Note: We will explore multidimensional grids (x, y, z) in Chapter 3).*

## 2.8.4 Runtime Application Programming Interface (API)

Finally, CUDA provides standard C-style library functions (the Runtime API) that allow the host (CPU) to manage the GPU's memory and control data movement.

> **Deep Dive:** [2.4 Device Global Memory and Data Transfer](./2.4_Device_global_memory_and_data_transfer.md)

- **`cudaMalloc`**: Allocates memory on the GPU (VRAM).
- **`cudaFree`**: Frees memory on the GPU (crucial to prevent memory leaks!).
- **`cudaMemcpy`**: Transfers data across the PCIe bus. It can copy from Host-to-Device (H2D), Device-to-Host (D2H), or even Device-to-Device (D2D).

Every single one of these API calls returns a `cudaError_t` enum, which should always be checked to ensure the operation succeeded!

> **Official Reference:** For any other CUDA API functions not covered here, the authors strongly recommend consulting the official [CUDA C Programming Guide (NVIDIA)](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html).

## The Authors' Core Philosophy & Intentions

The authors make a very important point at the end of this chapter regarding their teaching philosophy for the rest of the book:

1. **Not a Dictionary:** Chapter 2 is **by no means a comprehensive account of all CUDA features**. It is only meant to introduce the core concepts needed to write a *simple* CUDA C program.
2. **Concept Over Syntax:** Their emphasis moving forward will always be on the **key parallel computing concepts**. They will only introduce new CUDA C syntax when it is strictly necessary to implement a new parallel programming technique in their code examples.
3. **The Docs are Your Friend:** They reiterate that the book is not meant to replace the official documentation. Whenever you need the deepest technical details of a specific feature, the **[CUDA C Programming Guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html)** is the source of truth.
