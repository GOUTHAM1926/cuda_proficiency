# 2.2 CUDA C Program Structure

When writing a CUDA C program, the goal is to exploit data parallelism by writing code that runs simultaneously across thousands of cores.

A key feature of CUDA C is its seamless integration with standard C. **By default, any traditional C program is already a valid CUDA program that simply contains only host code.** To leverage the GPU, device code can be added directly into existing source files.

The structure of a CUDA C program reflects this coexistence, splitting code into two parts:

1. **Host Code (CPU):** Traditional, sequential C/C++ code executing on the CPU. It handles setup, memory management, data loading, and orchestrating GPU kernel launches.
2. **Device Code (GPU):** Parallel code executing on the GPU. Device code is designated using CUDA keywords (specifically `__global__`, `__device__`, and `__host__`, detailed in [§2.5](./2.5_Kernel_Functions_and_threading.md)) allowing the compiler to distinguish target architectures. Device functions known as **kernels** execute in a data-parallel manner.

When the CPU invokes a kernel function, the runtime instructs the GPU to instantiate a massive collection of threads. All threads spawned by a single kernel invocation collectively form a **Grid**. When the grid completes execution, control returns to the CPU host.

## The Cost of Threads: CPU vs GPU

A foundational concept in parallel computing is why spawning millions of threads on a GPU is efficient, whereas spawning even 1,000 threads on a CPU incurs severe overhead.

This architectural difference stems from two mechanisms: **Thread Generation** and **Thread Scheduling**.

### What Does "Generating" a Thread Mean?

Generating a thread refers to instantiating thread state in system memory so instruction execution can commence.

* **On a CPU:** Thread creation requires an operating system kernel call. The OS allocates a dedicated stack in RAM (typically 1 MB to 8 MB), sets up virtual memory page tables and security contexts, and registers the thread descriptor in the OS scheduler queue. This process requires **thousands of clock cycles**, making thread creation heavyweight.
* **On a GPU:** The GPU hardware is architected to instantiate threads directly in silicon. Thread generation requires zero OS intervention. The hardware increments an internal counter and maps thread identifiers directly to physical registers in the SM register file. This process requires **1 or 2 clock cycles**, rendering thread creation virtually instantaneous.

### What Does "Scheduling" a Thread Mean?

Scheduling defines instruction issue timing for active threads and managing execution context during memory stalls.

* **On a CPU:** When an out-of-order CPU switches execution from Thread A to Thread B, the OS performs a "Context Switch." Thread A's architectural register state must be saved to RAM, and Thread B's state restored from RAM into physical registers. Transferring context data across the memory bus incurs high latency, making CPU thread switching expensive.
* **On a GPU:** A GPU Streaming Multiprocessor (SM) contains a massive physical register file (e.g., 64K 32-bit registers in Ampere). When thread blocks are allocated to an SM, all active thread registers remain permanently resident on-chip for the entire thread lifetime. When Thread A stalls awaiting memory data, the hardware warp scheduler instantly switches instruction issue to Thread B. No data movement to DRAM occurs because Thread B's context already resides in on-chip SRAM. This context switch occurs with **zero clock cycle overhead**.

Because GPU threads are lightweight to instantiate and incur zero-overhead hardware scheduling, systems can launch millions of concurrent threads without saturating scheduling infrastructure.

## Deconstructing the "Thread" Abstraction

To understand how a massive Grid operates, the concept of a thread must be defined at the hardware execution level:

1. **A thread represents a sequential execution stream:**  
   A thread executes an instruction stream sequentially, in program order.

2. **A thread maintains code, execution coordinates, and state:**  
   Every thread possesses three fundamental attributes:
   * **The Code:** The compiled instruction sequence residing in memory.
   * **The Program Counter (PC):** The hardware register tracking the current instruction address.
   * **The State:** The values stored in private local registers and condition codes.

3. **Thread execution is strictly deterministic:**  
   A single thread never executes two independent instructions concurrently. Parallelism arises not from a single thread performing multiple tasks, but from thousands of sequential threads executing in parallel across distinct ALUs.

4. **Thread state can be inspected deterministically:**  
   Because each thread maintains private register allocations, execution state can be examined statement-by-statement. In a debugging session, halting a thread exposes its Program Counter and register values directly.

5. **CPU "Multi-threading" vs. GPU "Massively Parallel SIMT":**  
   CPU multi-threading typically refers to **Task Parallelism** (e.g., 4 to 16 threads executing distinct tasks such as UI rendering, networking, audio, and disk I/O).  
   CUDA employs **Single Instruction, Multiple Threads (SIMT)** data parallelism: a single kernel invocation instantiates a Grid of thousands or millions of threads. Every thread executes the identical kernel instructions, but evaluates unique built-in coordinates (`threadIdx`, `blockIdx`) to operate on distinct data elements across memory.
