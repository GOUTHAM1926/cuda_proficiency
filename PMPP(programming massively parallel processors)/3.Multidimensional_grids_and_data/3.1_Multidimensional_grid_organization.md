# Chapter 3: Multidimensional Grids and Data

## Chapter Roadmap & Transition from Chapter 2

Chapter 2 focused exclusively on **1D arrays** and **1D thread grids**:
- Example: Vector addition ($C[i] = A[i] + B[i]$)
- Thread indexing: A flat 1D formula (`i = blockIdx.x * blockDim.x + threadIdx.x`)
- Grid launch: `<<< (N + 255) / 256, 256 >>>` (1D grid of 1D blocks)

While 1D grids work well for linear lists, many computational domains are inherently multidimensional:
- **Images and video frames** are 2D grids of pixels $(x, y)$ or $(row, col)$.
- **Matrices** in linear algebra, machine learning, and deep learning (GEMM) are 2D arrays $(M \times N)$.
- **Volumetric scientific simulations** (fluid dynamics, weather models, CT scans) are 3D grids $(x, y, z)$.

Instead of requiring manual calculation of complex 2D or 3D coordinate arithmetic in software, CUDA natively supports **multidimensional thread grids and blocks** (1D, 2D, and 3D).

---

## Chapter 3 Scope

This chapter examines how CUDA maps multidimensional execution grids onto multidimensional data structures through three progressive workloads:

1. **Color to Grayscale Conversion (Section 3.2):**
   - Independent 2D pixel-by-pixel color channel calculation.
   - Introduction to 2D thread coordinates (`threadIdx.x`, `threadIdx.y`, `blockIdx.x`, `blockIdx.y`).
   - Linearizing 2D matrix coordinates into 1D memory space (row-major layout).

2. **Image Blur / 2D Convolution (Section 3.3):**
   - A stencil kernel where each output pixel depends on a neighborhood of surrounding input pixels.
   - Handling multidimensional boundary conditions and edge cases.

3. **Matrix Multiplication / GEMM (Section 3.4):**
   - The foundational compute kernel of modern high-performance computing and neural networks.
   - Row-column dot products computed using 2D grids.

These practical examples establish foundational intuition for data parallelism prior to detailed discussions of GPU hardware architecture, warp scheduling, memory hierarchies, and performance optimizations in Chapters 4 and 5.

# 3.1 Multidimensional Grid Organization

## Core Principles of Thread Identification

In CUDA, every thread in a grid executes the exact same kernel function (SPMD: Single Program, Multiple Data). 

Because every thread runs identical code, threads distinguish themselves and claim their specific slice of work purely through **coordinates**:

```
                       Kernel Function Code
                     (Identical for all threads)
                                |
             ┌──────────────────┼──────────────────┐
             ▼                  ▼                  ▼
       Thread (0, 0)      Thread (0, 1)      Thread (1, 0)
     Operates on:        Operates on:        Operates on:
     Pixel (0, 0)        Pixel (0, 1)        Pixel (1, 0)
```

Without unique coordinates, all threads would compute the exact same element, producing race conditions and zero parallel speedup.

As established in Chapter 2, threads are organized into a two-level hierarchy:
1. **Grid:** The top-level collection of all thread blocks allocated for a kernel launch, distributed across all available Streaming Multiprocessors (SMs) on the GPU.
2. **Block:** A collection of threads that execute together on a single SM (a single block is never split across multiple SMs). Threads within a block can synchronize and share fast on-chip shared memory.

> [!NOTE]
> **Hardware Boundary & Architecture Summary:**  
> In the classic CUDA execution model (Compute Capability < 9.0, including consumer GPUs like the RTX 3060):
> - Thread blocks are strictly isolated: two blocks cannot share memory, even when executing on the identical physical SM.
> - `__syncthreads()` synchronizes threads only within an individual block.
> - The hardware GigaThread scheduler distributes blocks across all available physical SMs to maximize execution throughput.  
> 
> In modern architectures (Compute Capability $\ge$ 9.0, including Hopper CC 9.0, Blackwell Datacenter CC 10.0, and Blackwell Consumer GeForce RTX 50-series CC 12.0):
> - **Thread Block Clusters:** Introduces an optional grouping level where blocks co-scheduled in the same cluster can directly access each other's shared memory via **Distributed Shared Memory (DSMEM)** both across different SMs and within the same SM.
> - **Consumer Blackwell vs Datacenter Blackwell:** While both support Clusters and DSMEM, consumer RTX 50 cards (`sm_120`) drive Tensor Cores using register-based `mma.sync.aligned` instructions (supporting native FP4). They do not contain Tensor Memory (TMEM), `wgmma`, or `tcgen05` instructions, which remain exclusive to datacenter hardware (`sm_100`).
> - Detailed hardware analysis, cross-access matrices, and official documentation proofs are documented in [hardware_clarity.md](../../hardware_clarity.md#blackwell-architecture-data-center-b200--gb200-vs-consumer-geforce-rtx-50-series).

Chapter 3 expands this two-level hierarchy from 1D linear arrangements into **2D planes** and **3D volumes**.

## Built-In Variables: Dimensions vs Coordinates

The execution configuration parameters provided in a kernel launch (`<<< gridDim, blockDim >>>`) configure the size and shape of the execution grid:

```cpp
kernelName<<<gridDim, blockDim>>>(arguments);
```

Within every thread running on the GPU, CUDA provides four built-in variables of type `dim3`:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        DIMENSIONS vs COORDINATES                       │
├───────────────────────────────────┬────────────────────────────────────┤
│   Dimensions (The Container Size) │  Coordinates (The Position Badge)  │
├───────────────────────────────────┼────────────────────────────────────┤
│ - `gridDim`: Total blocks in grid │ - `blockIdx`: Which block a thread │
│ - `blockDim`: Threads per block   │   belongs to                       │
│                                   │ - `threadIdx`: Position of the     │
│                                   │   thread inside that block         │
└───────────────────────────────────┴────────────────────────────────────┘
```

### 1. Dimension and Coordinate Ranges

The coordinate ranges are strictly bounded by their corresponding dimensions:

* **Block Coordinates (`blockIdx`):**
  * Spans from **`0` to `gridDim - 1`** along each axis.
  * For dimension $X$: `0 <= blockIdx.x < gridDim.x`
  * For dimension $Y$: `0 <= blockIdx.y < gridDim.y`
  * For dimension $Z$: `0 <= blockIdx.z < gridDim.z`
* **Thread Coordinates (`threadIdx`):**
  * Spans from **`0` to `blockDim - 1`** along each axis.
  * For dimension $X$: `0 <= threadIdx.x < blockDim.x`
  * For dimension $Y$: `0 <= threadIdx.y < blockDim.y`
  * For dimension $Z$: `0 <= threadIdx.z < blockDim.z`

```
Linear 1D Grid Example: gridDim.x = 4, blockDim.x = 256
┌──────────────────┬──────────────────┬──────────────────┬──────────────────┐
│  Block 0         │  Block 1         │  Block 2         │  Block 3         │
│  (blockIdx.x = 0)│  (blockIdx.x = 1)│  (blockIdx.x = 2)│  (blockIdx.x = 3)│
│                  │                  │                  │                  │
│  threadIdx.x:    │  threadIdx.x:    │  threadIdx.x:    │  threadIdx.x:    │
│  0, 1, ..., 255  │  0, 1, ..., 255  │  0, 1, ..., 255  │  0, 1, ..., 255  │
└──────────────────┴──────────────────┴──────────────────┴──────────────────┘
```

### 2. Global Index Calculation (Linearization)

Physical GPU VRAM is a contiguous 1D sequence of byte addresses from `0` to `N - 1`. Because threads are organized hierarchically, the programmer must convert the two-level coordinate `(blockIdx, threadIdx)` into a single 1D global index `i`:

$$\text{Global Index } i = (\text{blockIdx.x} \times \text{blockDim.x}) + \text{threadIdx.x}$$

```
                blockIdx.x * blockDim.x                   + threadIdx.x
       ┌─────────────────────────────────────┐          ┌─────────────┐
       │ Skips all threads belonging to all  │     +    │ Steps into  │
       │ earlier blocks                      │          │ this block  │
       └─────────────────────────────────────┘          └─────────────┘
```

The hardware does not calculate this global index automatically; the kernel code explicitly executes this arithmetic to allow each thread to identify its target array element:

```cpp
__global__ void vectorAddKernel(float* A, float* B, float* C, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        C[i] = A[i] + B[i];
    }
}
```

Detailed implementations and experimental benchmarks of this vector addition pattern are provided in:
- Source implementation: [`vector_add_exp2.cu`](../2.Heterogeneous_data_parallel_computing/vector_addition_experiments/vector_add_exp2.cu#L8-L19)
- Comprehensive theoretical analysis: [`2.3_Vector_Addition_Kernel.md`](../2.Heterogeneous_data_parallel_computing/2.3_Vector_Addition_Kernel.md) and [`2.5_Kernel_Functions_and_threading.md`](../2.Heterogeneous_data_parallel_computing/2.5_Kernel_Functions_and_threading.md)

### 3. Hardware Implementation: Special Registers (SRegs) and Machine Instructions

The variables `threadIdx`, `blockIdx`, `blockDim`, and `gridDim` are not variables stored in dynamic memory. They are mapped directly to hardware **Special Registers (SRegs)** inside each Streaming Multiprocessor:

| CUDA C++ Variable | Hardware Special Register (SASS) | Description |
|---|---|---|
| `threadIdx.x` | `SR_TID.X` (`%tid.x`) | Thread ID along the X dimension |
| `blockIdx.x` | `SR_CTAID.X` (`%ctaid.x`) | Cooperative Thread Array (Block) ID along X |
| `blockDim.x` | `SR_NTID.X` (`%ntid.x`) | Number of threads per block along X |
| `gridDim.x` | `SR_NCTAID.X` (`%nctaid.x`) | Number of blocks per grid along X |

When a kernel references `threadIdx.x` or `blockIdx.x`, the compiler generates native machine code (SASS) using the SM's physical register file:

```text
S2R R1, SR_TID.X;       // Reads physical thread index directly from hardware into R1
S2R R2, SR_CTAID.X;     // Reads physical block index directly from hardware into R2
IMAD R3, R2, R4, R1;    // Calculates global index: R3 = (R2 * R4) + R1
```

#### Detailed Breakdown of Hardware Registers (`R1`, `R2`, `R3`, `R4`):

On NVIDIA GPUs, each Streaming Multiprocessor contains a large physical **Register File** (for example, 64K 32-bit registers on Ampere GPUs like the RTX 3060). When a warp executes, each thread is assigned dedicated 32-bit general-purpose registers labeled `R0`, `R1`, `R2`, etc.:

1. **`R1` (Thread Coordinate Storage):**
   * Operation: `S2R R1, SR_TID.X;`
   * `S2R` stands for **Special Register to Register**.
   * The hardware copies the thread's physical ID along dimension X (`SR_TID.X`, corresponding to `threadIdx.x`) into general-purpose register `R1`.
2. **`R2` (Block Coordinate Storage):**
   * Operation: `S2R R2, SR_CTAID.X;`
   * The hardware copies the block's physical ID along dimension X (`SR_CTAID.X`, corresponding to `blockIdx.x`) into general-purpose register `R2`.
3. **`R4` (Block Dimension Storage):**
   * `R4` stores the number of threads per block (`blockDim.x`).
   * This value is loaded into general register `R4` from the constant memory bank (`c[0x0][...]`) where kernel launch parameters are staged, or from special register `SR_NTID.X`.
4. **`R3` (Global Index Output):**
   * Operation: `IMAD R3, R2, R4, R1;`
   * `IMAD` stands for **Integer Multiply-Add**.
   * It performs fused integer arithmetic in a single clock cycle:
     $$\text{Destination } R3 = (R2 \times R4) + R1$$
     $$\text{Global Index } i = (\text{blockIdx.x} \times \text{blockDim.x}) + \text{threadIdx.x}$$
   * The calculated result placed into `R3` serves as the base offset for all subsequent global memory address calculations (`LDG.E` for loading array elements and `STG.E` for storing results).

Because coordinates reside in hardware registers, thread index retrieval executes in single-cycle time with zero global memory latency.
